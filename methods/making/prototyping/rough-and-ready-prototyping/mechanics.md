# Rough & Ready Prototyping — Mechanics

A rapidly built, low-fidelity model of a concept — built to test assumptions before investing in development.
**Phase:** Making | **Category:** Prototyping

---

## Purpose Statements

Use these in the introduction — lead with why, not what:

- Make the idea tangible enough that real people can react to it
- Test the riskiest assumption before investing in development
- Stop ideas that aren't working before the cost of stopping becomes high
- Reduce the cost of learning by building less and testing earlier
- Create a cycle of build → test → learn → iterate rather than a long loop of build → hope

---

## Inputs

- **A concept to prototype** — typically a concept poster or value proposition poster from upstream work
- **A named critical assumption** — what must be true for this concept to work? what are you testing?
- **Materials** appropriate to the prototype format (see Stuff section)
- **A defined scenario** — the realistic situation a tester will be placed in when using the prototype
- **A task list** — the 4–8 tasks or steps that walk through the scenario

---

## Outputs

- A testable prototype at a fidelity appropriate to the current confidence level
- A defined scenario and task list for pairing with Think-Aloud Testing or Critique
- Tested or ready-to-test assumptions
- A decision: iterate, validate further, or eliminate

---

## Process

### Introduction

| Step | What to say |
|---|---|
| Frame the need | We have a concept — now we need to make it real enough to learn from |
| Name the principle | The goal is to build just enough to test our most critical assumption — not to build the finished product |
| Set the expectation | Rough is intentional. The less polished this looks, the more honest the feedback we'll get. |
| Connect to the stakes | A problem we find now costs 1x to fix. After we've built it, it costs 10x. After we've shipped it, 100x. |

### Instructions

| Step | What to say / do |
|---|---|
| Name the assumption | Before anyone builds anything: *"What's the one thing that must be true for this concept to work? That's what we're testing."* |
| Decide what to model | Use the three circles — physical, information, people — to decide what the prototype actually needs to include. Build only what the assumption touches. |
| Choose the format | Decide as a group: physical, screen-based, service? Match the format to the assumption being tested. |
| Define the scenario | Pick the scenario — in a workshop, select from a pre-written list or choose the highest-risk task |
| Plan the structure | Block out 4–8 screens or components: *"What are the steps someone needs to take to complete this scenario? One step = one screen or artifact."* |
| Divide and conquer | Assign screens or components to individuals or pairs. Agree on visual/language conventions before splitting up. |
| Set the time box | Name the build time clearly. Typical: 30–40 minutes for a screen-based prototype in a workshop. The constraint matters — it's what keeps it rough. |

### Execution

| Step | What to do / say |
|---|---|
| Monitor the build | Check in with groups — watch for over-investing in fidelity, empty placeholder content, and unlabeled incomplete areas |
| Hold the frame | If groups are polishing: *"Would someone be able to react to this if it were rougher? Then leave it rougher."* |
| Remind about content | *"Use realistic words and numbers — not placeholder text. Testers react to content as much as layout."* |
| Prompt marking of gaps | *"Anything you're not building needs a label — 'not available yet,' 'coming soon.' Testers shouldn't hit a dead end without knowing why."* |

### End

| Step | What to do |
|---|---|
| Reconvene | Bring groups back together before testing begins |
| Consistency pass | Quick review: do terminology, headings, and visual style match across screens? Fix obvious inconsistencies. |
| Confirm scenario and tasks | Verify the scenario and task list are documented and ready to hand to testers |
| Transition to testing | This prototype is the input to Think-Aloud Testing or Critique — confirm which happens next and what the test protocol is |

### Next Steps

| Step | What to do |
|---|---|
| Run the test | Pair with Think-Aloud Testing or Critique |
| Capture findings | What assumption held? What didn't? What surprised you? |
| Decide | Iterate (refine the prototype and test again), validate further (test with more people), or eliminate (the assumption didn't hold — stop investing) |
| Increase fidelity if warranted | As assumptions get validated, fidelity can increase proportionally |

## Stuff

- **Time:** 10 min planning + 10 min structure + 30–40 min build (typical workshop format)
- **A concept to prototype** — concept poster, value proposition poster, or written idea
- **Format-appropriate materials:**
  - *Screen-based:* PowerPoint or Keynote with device frame templates; wireframe component library; access to Icon Finder, Unsplash, and Google image search; device mockup frames (phone, tablet, browser)
  - *Physical:* paper, cardboard, index cards, tape, markers, foam, found objects
  - *Service:* props, physical space, people to role-play
- **Scenario list** — if facilitating a workshop, prepare 4–6 realistic scenarios for groups to choose from. This prevents time loss on scenario debate.
- **Device frame templates** — for screen-based prototypes, pre-built phone/tablet/browser frames as the canvas
- **Wireframe library** — reusable components (buttons, input fields, nav bars, icons, images) to speed building
