# Engine candidate — Contextual inquiry: the retrospective, artifact-anchored walkthrough

**Status:** Candidate learning for the Diamonds engine. Surfaced while preparing a current-state inquiry during the TKE Design Quality Measure Relaunch engagement (2026-09-10). Written project-agnostic. **Provenance caveat below — this came from *designing* the session, not yet from running it.** Shared for review, not for a decision here.

---

## The gap it fixes

The engine has **no Contextual Inquiry method of its own**. It exists only as a live "show me" variant referenced inside Interviewing:

- `methods/looking/ethnographic/interviewing/method.md` — comparison table ("Contextual inquiry | 'Show me' | Behavior + explanation in context") and the "interviewing plus observation, in the interviewee's environment" note
- `methods/looking/ethnographic/interviewing/resources/recipes.md` and `.../references.md` — same framing
- the to-be-built "ethnographic methods spectrum" visual (Try It Yourself → Observation → Interviewing → Contextual Inquiry)
- cited as an upstream source by Rose/Thorn/Bud, Affinity Clustering, and Creative Matrix

Every one of those references frames contextual inquiry as **live observation of work as it happens**. There is no guidance for the very common case where the work you need to understand has *already happened*.

## The learning

When the work being studied is already complete — a decision already made, a score already produced, an artifact already built — you cannot observe it live. Trying to ("show me how you'd do it") produces a from-scratch re-enactment that is neither the real thing nor an honest observation, and it burns the session.

The honest method in that case is a **retrospective, artifact-anchored walkthrough**:

> The participant drives *the artifact they actually produced*, and you have them **retrace the real steps on it** — "show me *where* you did that" — rather than narrate the process in the abstract.

Why the artifact anchor matters: an abstract "talk me through your process" invites an idealized account that smooths over exactly the friction, workarounds, and judgment calls you came for. Keeping the participant pinned to the real artifact forces the messy, true version to the surface — which is the value contextual inquiry gives in the live case, recovered for the retrospective one.

**Two supporting disciplines that travelled with it:**

1. **Retrace, don't describe.** Pull the participant back to specific points on the artifact whenever they drift into general process description. The specific beats the summary every time.
2. **Confirm the inputs; don't import them.** Prior write-ups of "how it was done" (a brief, a task card, someone's summary) are claims to verify in the room, not facts to build your questions on. If your questions assume an input was used, you've smuggled the assumption in — and an *absent* input is itself a finding. Establish what was actually in play, then probe only what's confirmed.

## Provenance / confidence — read before weighting this

- **n = 1, and pre-session.** This surfaced from *designing* one retrospective walkthrough, before the session was run. It has not yet been validated against how the session actually goes. Treat it as a hypothesis worth pressure-testing across more engagements, not a settled pattern.
- It is consistent with an existing engine note (`modes/mode-coaching.md`): observation-based methods simulate poorly because their value is in seeing the unexpected. The retrospective variant is a real-world analogue of the same caution — the unexpected lives in the artifact's messy detail, not in the tidy retelling.

## The open question for review (for Justin — not resolved here)

Where should this live? Two candidate homes, laid out neutrally:

**Option A — Enrich the existing Interviewing method.** Add contextual inquiry (both live and retrospective variants) as a fuller treatment within Interviewing, where it is already referenced.
- *For:* keeps the ethnographic family together; contextual inquiry is already framed as an interviewing variant; lighter footprint.
- *Against:* the retrospective walkthrough has enough distinct mechanics (artifact-anchoring, retrace-don't-describe, input-confirmation, time-boxing the high-value segments) that it may be cramped as a sub-note.

**Option B — Give Contextual Inquiry its own method folder** (`method.md`, `mechanics.md`, `teaching.md`, `resources/`), with the live and retrospective variants as its two modes.
- *For:* room to do the mechanics justice; matches how the spectrum visual already treats it as a distinct point; other methods already link to it as if it were standalone.
- *Against:* another method to maintain; check against the target method set (the training-programme methods) before adding scope.

This proposal deliberately does **not** choose. That's the call to make on review.
